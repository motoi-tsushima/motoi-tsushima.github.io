先日（2026年10月31日）、`SnowStack.EncodingProbe 1.3.0` をリリースしたことは、告知の通りです。  
`EncodingProbe` の開発に Claude Code を使用していることは、以前から説明しています。

`EncodingProbe` については、以下のページで解説していますので、ご存じない方はご覧ください。

[EncodingProbe の解説ページ](https://snow-stack.net/encodingprobe_probed_content/)

正確に言うと、`EncodingProbe` のクラスライブラリの文字エンコーディング解析処理は、私が手作業で開発した原型を土台にして、Claude Code でカスタマイズしたものです。  
`EncodingProbe.PowerShell` のコマンドレットは、完全に Claude Code で開発しています。

この記事では、`1.3.0` の開発で新たに試した Claude Code の使い方について、個人的な雑感を述べたいと思います。

## Claude Code の「作業記憶」と「作業専用自我」

Claude Code による開発では、まず開発用のフォルダーを決めて、そのフォルダー直下に `CLAUDE.md` を配置します。  
この `CLAUDE.md` が、そのフォルダーにおける Claude Code の「作業記憶」の役割を果たします。

開発中のソフトウェアの仕様や、人間の依頼者との対話の履歴など、`CLAUDE.md` だけでは収まりきらない情報もあります。  
そのような情報は、同じフォルダーの配下に複数のドキュメントとして配置して、長期的な「作業記憶」として保存します。

`EncodingProbe` の開発では、ソリューションフォルダーに `CLAUDE.md` を配置し、「作業記憶」を保存するドキュメントは `/docs/` フォルダーの配下にまとめています。  
Claude Code は、私と対話しながら `CLAUDE.md` と `/docs/` 配下のドキュメントを随時更新し、「作業記憶」を更新し続けます。

この「作業記憶」のドキュメントが、Claude Code の「自我」の一貫性を支えているのです。  
自我と言っても、人間の自我とは異なり、個々の作業の記憶の一貫性を維持するだけのものです。  
そこで、この記事では、これを「作業専用自我」と呼ぶことにします。（私の造語です）

「作業専用自我」は、フォルダーごとに作られます。  
作業用のフォルダーを変えて、別のフォルダーに `CLAUDE.md` と `/docs/` を配置すれば、その場所に別の「作業専用自我」を作成できます。  
よって、ソフトウェア開発では、「開発者自我」と「テスト用自我」を、別の人格を持つ「作業専用自我」として作ることができます。

## 「開発者自我」と「テスト用自我」を分離した

`1.2.0` 以前の開発では、「開発者自我」の Claude Code 一つだけで `EncodingProbe.PowerShell` を開発していました。  
テストも「開発者自我」に任せていました。

しかし、単一の「作業専用自我」だけに任せると、自分の開発したプログラムに対するテストが甘くなりがちで、充分に網羅的なテストができません。（人間でも同じです）

そこで `1.3.0` の開発では、新たな試みとして、「開発者自我」とは別のフォルダーに、別の `CLAUDE.md` と `/docs/` を配置して、「テスト用自我」を新規に作成しました。  
そして「テスト用自我」には、「バグを見つけ出すことだけを目的に、多様なテストを実行する」ことを依頼しました。

「開発者自我」と「テスト用自我」を分離したことで、「テスト用自我」は「開発者自我」の事情などお構いなしに、厳しいテストを実施しました。  
その結果、「開発者自我」も人間の私も想像しなかったようなテストパターンを多数試し、それまで見つけられなかった不具合を多数見つけ出しました。

「テスト用自我」の不具合報告を、私が「開発者自我」に渡してデバッグしてもらうことで、より信頼性の高いコマンドレットとクラスライブラリを開発できました。

ちなみに、「テスト用自我」を作ったのは今回が初めてではありません。  
前回の `1.2.0` の国際化対応のときも、暫定的に独立した「テスト用自我」を作成していました。  
しかし、今回ほど本格的なテストではなかったので、報告はしていません。

## 次はハーネスエンジニアリングを試したい

今回は、「開発者自我」と「テスト用自我」の間のやり取りを、人間の私が橋渡しする形で開発作業を進めました。  
しかし、この「やり取り」の部分は、間に「管理者自我」の Claude Code を置くことで、自動化できるようです。  
このような AI の作業環境の工夫は、「ハーネスエンジニアリング」と呼ばれる考え方に含まれるようです。

ハーネス（harness）とは、元々は馬具のことで、馬の力を制御して引き出すための道具です。  
ハーネスエンジニアリングは、AIエージェントそのものではなく、AIエージェントを取り巻く作業環境を設計する考え方を指すようです。  
ここで言う作業環境には、指示ファイルやドキュメント、AIに使わせるツール、自動テスト、結果を検証して手直しさせる仕組みなどが含まれます。  
複数の AIエージェントに役割を分担させ、管理役のエージェントにそれらを連携させる仕組みも、その一部です。

つまり、「管理者自我」による自動化は、ハーネスエンジニアリングの一部に過ぎません。  
見方によっては、今回の `CLAUDE.md` と `/docs/` による「作業記憶」の仕組みも、ハーネスエンジニアリングの一種と言えるかも知れません。  
（私自身もまだ勉強中なので、この説明は大まかなもので、正確ではない部分があるかも知れません）

次回は、「管理者自我」による自動化を中心に、ハーネスエンジニアリングを試してみるつもりです。

最近は、AI社員など、次々と新しいAI駆動開発の手法が生み出されていて、私は最先端の手法には、なかなか追いつけないでいます。  
私は、私の能力の範囲内でしか進めないので、マイペースでゆっくりと AI駆動開発を習得していこうと思っています。
